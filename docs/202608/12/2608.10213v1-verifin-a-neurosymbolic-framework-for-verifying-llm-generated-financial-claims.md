## 摘要
大型语言模型通常能从财务申报文件中生成看似合理的数字声明，但可能使用了错误的报告期、单位、行项目或公式。验证此类声明不仅需要重新检查算术：验证者必须确定相关事实，建立授权计算，并判断候选值是否由两者共同推导得出。我们提出VeriFin，一种用于数值财务问答的神经符号验证框架，该框架将操作数锚定在已申报的XBRL事实中，从问题、申报链接库或文档化的指标定义中推导计算，并使用Z3检查声明。当声明不一致时，求解器导出的不可满足核心可识别冲突的事实、公式和候选值，从而实现有针对性的修复。我们在XBRLFiling（一个由28家美国公司的10-K申报文件构建的包含600个问题的新基准）和FinanceBench上评估了VeriFin。在由所有验证方法共享的固定候选池中，VeriFin未接受任何不正确的声明，而基线方法在XBRLFiling的600个声明中接受了6至92个不正确的声明，在FinanceBench的67个声明中接受了4至21个不正确的声明。零误接受的结果在多个答案生成器模型中保持一致。求解器导出的反馈进一步改善了修复，在真实捕获中实现了高达69.9%的恢复率。这些结果表明，基于来源的符号验证可以为LLM生成的财务声明提供可靠且可审计的接受控制。

## Abstract
Large language models often produce plausible numerical claims from financial filings while using the wrong reporting period, unit, line item, or formula. Verifying such claims requires more than rechecking arithmetic: a verifier must ground the relevant facts, establish the authorized calculation, and determine whether the candidate value follows from both. We propose VeriFin, a neurosymbolic verification framework for numerical financial question answering that grounds operands in filed XBRL facts, derives calculations from the question, filing linkbases, or documented metric definitions, and checks claims using Z3. When a claim is inconsistent, solver-derived unsatisfiable cores identify the conflicting facts, formula, and candidate value, enabling targeted repair. We evaluate VeriFin on XBRLFiling, a new 600-question benchmark constructed from 10-K filings of 28 U.S. companies, and on FinanceBench. On fixed candidate pools shared by all verification methods, VeriFin accepts none of the incorrect claims, whereas the baselines accept 6 to 92 incorrect claims on XBRLFiling's 600 claims and 4 to 21 incorrect claims on FinanceBench's 67 claims. The zero false-accept result persists across multiple answer-generator models. Solver-derived feedback further improves repair, achieving up to 69.9% recovery among true catches. These results show that source-grounded symbolic verification can provide a reliable and auditable acceptance control for LLM-generated financial claims.

## 1. 核心问题与整体含义

- **背景**：金融专业人士越来越多地使用大语言模型（LLM）回答关于上市公司申报文件的数值问题。这类问题通常涉及从 10-K/10-Q 文件中识别正确的行项目、报告期、单位和计算公式。
- **核心问题**：LLM 生成的财务声明往往"听起来合理"但实际错误——可能使用了错误的报告期、单位、规模、符号、指标定义或事实来源。错误一旦进入估值模型、风险报告或投资备忘录，将难以追踪和发现。因此，**可靠性问题不只是 LLM 能否生成答案，而是该答案是否应被接受进入财务工作流**。
- **研究定位**：不同于传统的"LLM 生成的答案是否正确"的生成侧改进，本文将问题重构为**验收控制问题**（acceptance control）：给定一个 LLM 生成的固定数值声明，财务工作流是否应当接受它？这需要独立于候选答案本身，建立事实基础与授权计算，再对声明进行验证。

## 2. 方法论：VeriFin 框架

### 核心思想

- **神经符号分离**：语言模型仅用于语义解析和检索规划（负责提出候选答案和验证计划），而算术执行、上下文绑定和一致性检查全部交由确定性 XBRL 链接库和 SMT 求解器 Z3 完成。
- **非对称工作流**：验证一个问题的答案比生成答案更容易——候选声明被当作"不可信声明"，**绝不影响**验证所用的权威事实和公式。
- **验收决策**：仅由"锚定的事实 + 授权公式"是否构成可满足的约束系统来决定。

### 五个组件

1. **证据检索器（Evidence Retriever）**
   - 从文档中选择有界数量的证据块，防止跨文件污染；
   - 识别所需行项目事实，构建扩展查询；
   - 混合打分函数：`S(q_i, c) = cos(e(q_i), e(c)) + λ·S_lex(q_i, c)`，结合稠密余弦相似度与词汇精确匹配得分。

2. **答案生成器（Answer Generator）**
   - 基于检索到的证据生成候选声明 a，**故意与决策解耦**，仅作为待验证目标。

3. **验证规划器（Verification Planner）**
   - 用 LLM 将问题和证据解析为验证计划 C = (M, F, R, u, ρ, S)，包含目标指标、授权公式、操作数角色、预期单位、报告期和公式来源；
   - 公式来源遵循严格层级：题干明确操作 → 申报链接库 → 指标注册表 → 披露文本；如果公式来源不完整或不明确，则弃权（Abstain）。

4. **出处验证器（Provenance Verifier）**
   - **概念绑定**：按三级策略将操作数角色解析为XBRL概念——计算链接库直接绑定 → 注册表匹配 → 符号标签启发式匹配；
   - **时期与单位绑定**：仅绑定报告期匹配且单位匹配的事实，并按请求规模归一化；
   - **值绑定**：操作数值完全取自申报事实，注册表解析的概念采用"value-blind"绑定（不信任模型提取的值）；
   - 每个绑定记录概念、时期、单位、accession号及来源事实标识，完全可追溯。

5. **声明验证器（Claim Verifier）**
   - 构建约束系统：`Φ = (∧(x_i = m_i*)) ∧ (v̂ = f(x)) ∧ (|v̂ - v_c| ≤ τ)`
   - 编译为无量词实数算术，由 Z3 判定：可满足 → Verified；不可满足 → Violated；无法建立事实/公式 → Abstain；
   - 容差 τ 为申报披露精度的半个最小单位（如百万单位则 τ=0.5 百万）；
   - **UNSAT core 反馈**：命名每个约束，冲突时提取不可满足核心，明确指认冲突的申报值、行项目角色、公式与候选值边界，为修复提供精确诊断。

## 3. 实验设计

### 数据集

1. **XBRLFiling（新构建基准，N=600）**
   - 从 EDGAR 收集 28 家美国公司（苹果、微软、亚马逊、英伟达、埃克森美孚等）的 86 份 10-K 申报，财年 2021–2026；
   - 覆盖 3 张主要报表、15 个目标小计（净利润、流动资产、营业收入、各类现金流等）；
   - 构建方式：从申报文件中计算链接库声明的计算关系出发反向生成问题——模板生成问题，金标准答案是申报中的实际值；
   - 关键设计：目标年份的小计值被遮蔽（[redacted]），前一年数值完整保留在旁，构成"貌似合理但错误"的候选，迫使模型正确选择报告期并独立计算。

2. **FinanceBench（n=67）**
   - 公开基准中的人工标注数值子集，覆盖真实 10-K/10-Q 文件的开放式问题，非由 XBRL 链接库构建。

### 对比方法与设置

- **固定候选池**：所有验证方法评估完全相同的候选声明和证据，差异仅反映验证方法行为。
- **验证基线**（均以 Claude Haiku 4.5 为验证骨干）：

  - LLM Judge：LLM 收到问题、证据和声明，判断是否接受；

  - Program-of-Thought (PoT)：生成 Python 程序执行，数值输出用容差规则比较。
- **答案生成模型（6个）**：GPT-5.5、Claude Haiku-4.5、Qwen3-30B、Llama-3.1-8B、Qwen2.5-7B、Fin-o1-8B。温度 0，2048 token 限制。

## 6. 主要结论与发现

- **零误接受**：在 XBRLFiling 上，VeriFin 拒绝了全部 92 个错误候选，基线接受了 6–92 个；在 FinanceBench 上，VeriFin 拒绝全部 21 个错误候选，基线接受了 4–21 个。
- **高精度与合理覆盖率**：XBRLFiling 上精度 100%、准确率 92.2%、覆盖率 98.8%（弃权率 1.2%）；FinanceBench 上精度 100%、准确率 83.3%、覆盖率 80.6%。
- **跨模型稳健**：12 个模型-数据集组合全部零误接受，证明结果不依赖于特定候选生成模型。
- **信息不等于执行**：Judge+Formula 收到了正确公式和值，仍接受了 75 个错误声明（XBRLFiling），说明仅向 LLM 提供正确计算信息不足以使其可靠执行——必须编码为硬约束。
- **覆盖率代价明确**：正确声明中 37–73 个被拒绝（取决于生成模型）；覆盖率在复杂开放式问题（FinanceBench）下显著下降（80.6%），体现了安全性-覆盖率的权衡。
- **可解释修复有效**：UNSAT core 引导修复在 pass@1 上比通用重试提升最多 39.8 个百分点，pass@3 最高达到 69.9%（Fin-o1-8B 在 XBRLFiling）。

## 7. 优点

- **神经符号设计清晰**：将"提出答案"与"验证答案"彻底分离，从根本上避免候选声明对验证过程的循环污染。
- **可审计性与可追溯性**：每个操作数绑定到具体 XBRL 事实（概念、时期、单位、accession号），每个公式记录来源授权链，决策完全确定性且可回溯到文件证据。
- **明确的弃权机制**：将"无法验证"作为显式的财务控制决策，而不是用模型假设填补空白，避免伪确定性。
- **UNSAT core 诊断**：符号验证天然带来的副产品被创新性地用于修复反馈，提供精确失败定位，超越二元判断或自然语言批评。
- **严谨的基准构建**：XBRLFiling 从申报文件声明的计算关系反向构建，每个问题都携带机器可检查的签名操作数和可追溯的金标准值；遮蔽设计迫使其正计算而非直接读取。
- **实验设计公平**：固定候选池、温度 0、明确的数值匹配规则，确保基线不因候选生成差异而失真。

## 8. 不足与局限

- **覆盖率受限**：在 FinanceBench 等更开放、非链接库构建的问题集上覆盖率仅 80.6%，正确答案也可能因无法建立授权公式或锚定事实而被拒绝（最多 73 个正确声明被拒）。
- **对 XBRL 基础设施的依赖**：核心优势依赖申报文件已发布的计算链接库和结构化 XBRL 事实；对未采用 XBRL 或链接库不完备的文件，验证能力显著受限。
- **验证范围有限**：仅验证可直接由授权公式计算的数值声明；对需要主观判断、自由文本注释或跨文件综合推理的声明不适用。
- **首轮验证成本**：每个问题 4–6 次 LLM 调用和 12k–17k tokens，在超大规模部署中成本和延迟可能成为瓶颈。
- **未明确算力细节**：未报告模型推理环境的 GPU 配置、能耗或预算，影响可复现性和成本评估。
- **指标"零误接受"的统计范围**：零误接受是在固定候选池和有限样本上观察到的结果，并非数学保证；论文未提供置信区间或更严格的理论保证（尽管 Z3 的确定性是可靠的，但候选生成和计划解析环节仍有 LLM 引入的不确定性）。
- **修复实验局限**：仅覆盖三个修复骨干模型，未报告跨全部六种生成模型的修复结果；评分病例数波动导致只能做描述性解读而非统计推断。
